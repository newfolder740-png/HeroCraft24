Аудит UI-рендеринга карточек HeroCraft24
=========================================
Дата: 2026-08-08
Источники: 01_architecture_report.txt, 02_model_audit.txt, анализ исходного кода


A) Повторяющиеся UI-паттерны
------------------------------

1. addSection + addRow + addText — тройная реализация
   Три файла содержат идентичные реализации:
   - ReferenceDetailFragment.kt: строки ~1970-2020
   - EquipmentDetailFragment.kt: строки ~97-125
   - SpellDetailFragment.kt: строки ~130-160

   Три метода с одинаковой сигнатурой и логикой:
   - addSection(title, block) — создаёт заголовок TitleMedium + LinearLayout-контейнер
   - addRow(label, value) — TextView с жирным label и обычным value
   - addText(text) — TextView BodyMedium с padding

   Различия:
   - ReferenceDetailFragment учитывает activeRenderContainer (для ViewPager2)
   - EquipmentDetailFragment и SpellDetailFragment пишут в binding.detailContent
   - Padding значения совпадают (0,4,0,4 для addRow/addText; 0,24,0,8 для addSection)

2. Expandable card — 5 реализаций с одинаковой структурой
   Каждая создаёт MaterialCardView → inner LinearLayout → title TextView →
   body LinearLayout (isVisible=false) → toggle по card.setOnClickListener.

   | Карточка            | Файл        | Строка  | open-ids set          | table | desc2 | subtitle |
   |---------------------|-------------|---------|-----------------------|-------|-------|----------|
   | createFeatureCard   | RefDetail   | ~1120   | openFeatureIds        | ✓     | ✓     | level    |
   | createInvocationCard| RefDetail   | ~730    | openInvocationIds     | ✓     | ✓     | level+req|
   | createMetamagicCard | RefDetail   | ~530    | openMetamagicIds      | ✗     | ✗     | cost     |
   | createManeuversCard | RefDetail   | ~560    | openManeuversIds      | ✗     | ✗     | ✗        |
   | createSchemsCard    | RefDetail   | ~590    | openSchemsIds         | ✓     | ✓     | ✗        |
   | createSpeciesTraitCard| RefDetail  | ~1310  | нет (не сохраняет)    | ✓     | ✓     | level    |
   | createClassSubclassCard| RefDetail | ~410   | нет (не сохраняет)    | ✓     | ✓     | ✗        |

   Общий код каждой карточки: 30-40 строк boilerplate (card params, inner layout,
   title, body, toggle). Меняются только: title-формат, subtitle, body-контент,
   и open-ids set для сохранения состояния.

3. buildRichLinkedTextView / linkify — 3 реализации
   - ReferenceDetailFragment.kt: buildRichLinkedTextView (строка ~2200)
     использует getCombinedBucketsCache() + ItemLinkifier
   - EquipmentDetailFragment.kt: linkify (строка ~131)
     использует vm.itemNameToIdMap + spellNameToIdMap + conditionNameToIdMap
   - SpellDetailFragment.kt: buildLinkedTextView (строка ~100)
     использует только viewModel.conditionNameToIdMap

   Все три делают: stripMarkers → SpannableStringBuilder → findRanges →
   setSpan(ClickableSpan) → navigateToDetail. Разница в:
   - источнике name-маппингов (vm-поля vs getCombinedBucketsCache)
   - навигации (navigateToReference vs Navigation.findNavController)
   - обработке explicitLinks (есть только в RefDetail и EquipDetail)

4. addSourceSection — 3 реализации
   - ReferenceDetailFragment.kt: addSourceSection(source) (строка ~2270)
   - EquipmentDetailFragment.kt: inline в render() (строка ~86)
   - SpellDetailFragment.kt: inline в render() (строка ~125)

   Формат: "${source.book.get()} (${source.abbreviation})${page?}",
   различается только форматирование страницы (", p. $it" vs ", с. $it").

5. localizeSchool — 3 реализации
   - SpellsViewModel.kt: строки ~185-194
   - SpellListAdapter.kt: (внутри адаптера)
   - SpellDetailFragment.kt: localizeSchool (строка ~112)
   - ReferenceDetailFragment.kt: localizeSpellSchool → делегирует UiLocalizer

   При этом UiLocalizer уже предоставляет канонические версии, но
   SpellDetailFragment не использует его, а имеет собственный when-блок.

6. Localize-функции: 6+ копий when-блоков
   - localizeCategory: RefDetail (строка ~1170) + EquipDetail (делегирует UiLocalizer)
   - localizeRarity: RefDetail → UiLocalizer + EquipDetail → UiLocalizer
   - localizeDamageType: RefDetail → UiLocalizer + EquipDetail → UiLocalizer
   - localizeProperty: RefDetail → UiLocalizer + EquipDetail → UiLocalizer
   - localizeCondition: RefDetail (строка ~1800) — 15-entry when
   - localizeEnvironment: RefDetail (строка ~1840) — 30+ entry when
   - localizeAlignment: RefDetail (строка ~1810) — сложная логика
   - localizeAbility: RefDetail (строка ~1900) — 6-entry when
   - localizeSkill: RefDetail (строка ~1910) — 18-entry when
   - localizeSense: RefDetail (строка ~1780) — 5-entry when
   - localizeSubcategory: RefDetail (строка ~1180) — 10-entry when
   - localizeCostUnit: RefDetail (строка ~1190) — 5-entry when
   - localizeWeightUnit: RefDetail (строка ~1195) — 2-entry when


B) Хардкод порядка
-------------------

1. renderClassMainTab — захардкоженный порядок блоков
   Файл: ReferenceDetailFragment.kt, строка ~395
   Порядок: class_table → acquisition → key_attributes → starting_equipment →
   features → source → references
   Если добавить новый блок (например, spellcasting details), нужно менять метод.

2. renderMonster — 15 последовательных addSection
   Файл: ReferenceDetailFragment.kt, строки ~1650-1750
   Порядок: quick_stats → ability_scores → skills → senses → resistances →
   vulnerabilities → dmg_immunities → cond_immunities → languages →
   environment → treasure → equipment → traits → actions → bonus_actions →
   reactions → legendary_actions → mythic_actions → lair_actions →
   description → table → description2 → source
   23 блока, каждый проверяет nullable-поле. Порядок не может быть изменён
   без правки метода.

3. renderSpell — 2 реализации с разным порядком
   - ReferenceDetailFragment.renderSpell() (строка ~1600):
     quick_info → description → table → description2 → higher_levels → classes → source
   - SpellDetailFragment.render() (строка ~68):
     quick_info → description → higher_levels → damage → classes → subclasses → source
   Разный порядок: higher_levels/damage/table идут в разной последовательности.
   У SpellDetailFragment есть damage-секция, у RefDetail — нет.
   У RefDetail есть table/description2, у SpellDetail — нет.

4. renderItem — 2 реализации с разным порядком
   - ReferenceDetailFragment.renderItem() (строка ~1500):
     quick_info → description → table → description2 → source
   - EquipmentDetailFragment.render() (строка ~55):
     quick_info → description → effects → source
   Разный порядок: effects-секция есть в EquipmentDetail, но в RefDetail
   она встроена в quick_info как addRow. description2/table есть в RefDetail,
   но отсутствуют в EquipmentDetail.

5. renderSpecies — захардкоженный порядок
   Файл: ReferenceDetailFragment.kt, строка ~1260
   Порядок: quick_info → description → subspecies → traits → table →
   description2 → source

6. renderBackground — захардкоженный порядок
   Файл: ReferenceDetailFragment.kt, строка ~1340
   Порядок: description → ability_score_increases → skills → tools →
   equipment → feat → table → description2 → source

7. renderFeat — захардкоженный порядок
   Файл: ReferenceDetailFragment.kt, строка ~1640
   Порядок: quick_info → description → benefits → source

8. renderCondition — захардкоженный порядок
   Файл: ReferenceDetailFragment.kt, строка ~1630
   Порядок: description → effects → source

9. renderMechanic — захардкоженный порядок
   Файл: ReferenceDetailFragment.kt, строка ~1620
   Порядок: description → table → description2


C) Кандидаты на общий компонент
---------------------------------

1. ExpandableCard — унифицировать 7 карточек
   Общий интерфейс:
   - title: String (или SpannableString)
   - subtitle: String? (cost, level, requirements)
   - body-контент: list of ViewBuilders
   - openId: String? (для сохранения expanded state)
   - onClick: toggle body.isVisible + update openId set

   Затронет: createFeatureCard, createInvocationCard, createMetamagicCard,
   createManeuversCard, createSchemsCard, createSpeciesTraitCard,
   createClassSubclassCard — все в ReferenceDetailFragment.kt

2. CardBuilder — общий helper для addSection/addRow/addText
   Унифицировать 3 реализации (RefDetail, EquipDetail, SpellDetail) в один
   объект в core:ui. Методы:
   - addSection(title, block)
   - addRow(label, value)
   - addText(text)
   - addLinkedText(text, linkMap)
   - addSourceSection(source)
   Параметризовать renderTarget (LinearLayout) и context.

3. RichTextLinkifier — унифицировать 3 реализации linkify
   Общий метод: linkify(text, nameMap, navigateFn) → SpannableStringBuilder
   Источник nameMap: делегировать ViewModel/Repository (метод getCombinedNameMap).
   Навигация: передавать лямбду (fullId) → Unit.

4. LocalizeRegistry — вынести все when-блоки в UiLocalizer
   Уже частично сделано (UiLocalizer в core:ui), но:
   - SpellDetailFragment.localizeSchool не использует UiLocalizer
   - RefDetail.localizeCondition, localizeEnvironment, localizeAlignment,
     localizeSense, localizeSkill, localizeSubcategory — не в UiLocalizer
   - EquipDetail делегирует UiLocalizer, но RefDetail — нет (для некоторых)
   Перенести все when-блоки из RefDetail в UiLocalizer.

5. SourceSectionBuilder — общий компонент для "Источник"
   Формат: "${book} (${abbr})${page?}"
   Унифицировать ", p. $it" (RefDetail) vs ", с. $it" (EquipDetail).
   Параметризовать локаль страницы.


D) Рискованные места
---------------------

1. SpeciesTraitCard — не сохраняет expanded state
   Файл: ReferenceDetailFragment.kt, createSpeciesTraitCard (строка ~1310)
   Проблема: card.setOnClickListener { body.isVisible = !body.isVisible }
   без обновления openId-множества. При повороте экрана или навигации
   назад/вперёд все trait-карточки схлопнутся.
   Сравнение: FeatureCard, InvocationCard, MetamagicCard, ManeuversCard,
   SchemsCard — все сохраняют openId.

2. ClassSubclassCard — не сохраняет expanded state
   Файл: ReferenceDetailFragment.kt, createClassSubclassCard (строка ~410)
   Проблема: аналогично SpeciesTraitCard — нет openId-множества.
   Карточки подклассов всегда схлопнутся при пересоздании.

3. renderSpell в RefDetail — нет damage-секции
   Файл: ReferenceDetailFragment.kt, renderSpell (строка ~1600)
   Проблема: SpellDetailFragment отображает damage (damage_type, damage_at_slot_level,
   damage_at_character_level), но renderSpell в RefDetail — нет.
   Пользователь видит разный контент в зависимости от того, как он попал
   на карточку заклинания (через справочник → меньше данных, через спеллы → больше).

4. renderItem в RefDetail — нет effects-секции как отдельного блока
   Файл: ReferenceDetailFragment.kt, renderItem (строка ~1500)
   Проблема: effects встроены в quick_info как addRow (многострочный текст),
   а EquipmentDetailFragment показывает их как отдельный блок с bullet points.
   Для предметов с 3+ эффектами quick_info становится перегруженным.

5. renderItem в RefDetail — нет description2/table
   Файл: ReferenceDetailFragment.kt, renderItem (строка ~1570)
   Примечание: в коде ЕСТЬ addSection для table и description2 (строки ~1575-1576),
   но EquipmentDetailFragment.render() не имеет этих секций вообще.
   Если у предмета есть table/description2, EquipDetail их не покажет.

6. renderMonster — description в конце
   Файл: ReferenceDetailFragment.kt, renderMonster (строка ~1740)
   Проблема: описание монстра (fluff-текст) отображается ПОСЛЕ всех игровых
   характеристик (действия, реакции и т.д.). Это 23-й блок. Для больших
   монстров пользователь может не добраться до описания.
   При этом для Species/Background/Feat описание идёт вторым блоком.

7. FeatureCard — ленивый linkify с placeholder
   Файл: ReferenceDetailFragment.kt, createFeatureCard (строка ~1160)
   Проблема: при первом раскрытии карточки placeholder-TextView заменяется
   на linked-TextView. Если карточка была сохранена в openFeatureIds,
   при восстановлении замена происходит корректно. Но если между созданием
   и восстановлением изменился combinedNameMap (например, загружен новый pack),
   ссылки могут быть некорректными.

8. createManeuversCard — не отображает cost
   Файл: ReferenceDetailFragment.kt, createManeuversCard (строка ~560)
   Проблема: Maneuvers-модель не имеет поля cost (см. 02_model_audit.txt #2),
   но даже если бы имела, карточка не показывает subtitle. В отличие от
   createMetamagicCard, которая показывает cost в заголовке.
   Пользователь не видит стоимость манёвра.

9. SpellDetailFragment.buildLinkedTextView — не использует ItemLinkifier
   Файл: SpellDetailFragment.kt, buildLinkedTextView (строка ~100)
   Проблема: ручной поиск по conditionNameToIdMap вместо ItemLinkifier.
   Не обрабатывает: stripMarkers, explicitLinks, excludedRanges, stem matching.
   Любые @@-маркеры в тексте заклинания будут показаны как есть.

10. RefDetail.renderSpell — хардкод русских строк
    Файл: ReferenceDetailFragment.kt, renderSpell (строка ~1600)
    Проблема: "Заговор", "Уровень", "Школа", "Время сотворения", "Длительность",
    "Дистанция", "Компоненты", "Материальный", "Концентрация", "Ритуал",
    "Спасбросок", "Тип атаки", "Область", "Улучшения", "Классы" —
    все захардкожены по-русски. SpellDetailFragment использует getString(R.string.*).
    При добавлении EN-локали RefDetail будет показывать русские заголовки.


E) Минимальный план унификации
-------------------------------

Шаг 1. Вынести addSection/addRow/addText в core:ui
   Создать: core/ui/render/CardBuilder.kt
   Содержимое: object CardBuilder с методами addSection, addRow, addText,
   addLinkedText, addSourceSection. Параметр renderTarget: LinearLayout.
   Затронет: 3 файла (RefDetail, EquipDetail, SpellDetail).
   Риск: низкий — чисто механическая замена, не меняет UI.

Шаг 2. Вынести ExpandableCard в core:ui
   Создать: core/ui/render/ExpandableCard.kt
   Содержимое: data class ExpandableCardParams + fun createExpandableCard().
   Параметры: context, title, subtitle?, bodyViews, openId?, openIdsSet.
   Заменить: 7 createXxxCard-методов в RefDetail.
   Риск: средний — нужно убедиться, что все варианты body-контента
   покрываются. MetamagicCard и FeatureCard имеют нестандартные subtitle
   (cost / level-префикс), но это решается параметром subtitle.

Шаг 3. Вынести linkify-логику в core:ui
   Создать: core/ui/render/RichTextLinkifier.kt
   Содержимое: fun linkify(text, nameMap, excludedRanges, explicitLinks, onClick).
   Заменить: 3 реализации (RefDetail.buildRichLinkedTextView,
   EquipDetail.linkify, SpellDetail.buildLinkedTextView).
   Риск: низкий — логика идентична, различаются только source map и navigate.

Шаг 4. Перенести все localize-функции в UiLocalizer
   Перенести из RefDetail: localizeCondition, localizeEnvironment,
   localizeAlignment, localizeSense, localizeSkill, localizeSubcategory,
   localizeCostUnit, localizeWeightUnit.
   Заменить SpellDetailFragment.localizeSchool на UiLocalizer.school.
   Риск: низкий — чисто механический перенос.

Шаг 5. Исправить renderSpell в RefDetail — добавить damage-секцию
   Добавить секцию "Урон" в renderSpell() по аналогии с SpellDetailFragment.
   Формат: damage_type + damage_at_slot_level + damage_at_character_level.
   Риск: низкий — только добавление контента, не затрагивает существующий.

Шаг 6. Исправить SpeciesTraitCard и ClassSubclassCard — сохранять expanded state
   Добавить openSpeciesTraitIds и openSubclassIds множества.
   Обновить onClick для записи/удаления id.
   Добавить сохранение/восстановление в onSaveInstanceState.
   Риск: низкий — добавление, не затрагивает существующую логику.

Шаг 7. Унифицировать renderMonster — description после quick_stats
   Переместить блок description сразу после quick_stats (как в Species/Background).
   Риск: средний — меняет визуальный порядок, но улучшает UX.

Шаг 8. Заменить хардкод русских строк в RefDetail.renderSpell на getString(R.string.*)
   Риск: низкий — механическая замена, не меняет UI.
