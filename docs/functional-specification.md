## 1. Общие положения

### 1.1. Терминология

| Термин | Определение |
|---|---|
| **Игровой объект** | Любая сущность из JSON-файлов: заклинание, предмет, класс, вид, происхождение, черта, состояние, монстр, механика, термин глоссария |
| **Пользовательские данные** | Данные, созданные пользователем и хранящиеся в Room: персонажи, избранное, настройки |
| **Пакет** | Именованный набор игровых объектов с общим источником (например, `phb2024`) |
| **Полный ID** | Строка формата `packId:objectId`, глобально уникальный идентификатор |
| **Локальный ID** | `objectId` — уникален только в пределах пакета |
| **Манифест** | `manifest.json` — индекс всех объектов пакета с краткой информацией |
| **Разрешение ссылки** | Процесс получения полного игрового объекта по его строковому ID |
| **Переиндексация** | Полное перестроение поискового индекса и кэша после изменения состава пакетов |

### 1.2. Соглашения о форматах

- Даты: ISO 8601 (`YYYY-MM-DDTHH:mm:ssZ`) в UTC
- Валюта: cp (медь), sp (серебро), gp (золото), pp (платина). 1 gp = 10 sp = 100 cp = 1/10 pp
- Вес: фунты (lb), всегда с одним десятичным знаком
- Время заклинаний: строковое представление (`"1 action"`, `"1 minute"`, `"10 minutes"`, `"1 hour"`, ...)
- Дистанция: футы (ft)
- Броски кубиков: строки формата `"2d8+3"` или `"8d6"`

### 1.3. Состояния приложения

Приложение находится в одном из трёх глобальных состояний:

| Состояние | Описание |
|---|---|
| **Инициализация** | Приложение запущено, но игровые данные ещё не загружены. Пользователь видит экран загрузки. |
| **Готовность** | Все пакеты загружены, индексы построены, приложение готово к работе. |
| **Ошибка** | Критическая ошибка, препятствующая работе (например, повреждена БД). Пользователь видит экран ошибки с кнопками восстановления. |

## 2. Управление персонажами

### 2.1. Создание персонажа

**Назначение:** Создание нового персонажа D&D 2024 через пошаговый мастер.

**Триггер:** Нажатие FAB «+» на экране списка персонажей или кнопки «Создать персонажа» в пустом состоянии.

**Предусловия:**
- Загружен хотя бы один пакет с классом, видом и происхождением
- Если пакетов нет — показать ошибку с предложением импортировать пакет

**Входные данные:** Нет (мастер собирает данные пошагово).

---

#### 2.1.1. Шаг 1: Выбор вида (Species)

**Поток:**
1. Система загружает список всех доступных видов из `ContentRepository.getAllSpecies()`
2. Список фильтруется: только виды из активных пакетов
3. Пользователь выбирает вид
4. Если у вида есть подвиды (subspecies):
   - Система показывает список подвидов
   - При выборе подвида — его traits и ability_score_increases заменяют родительские
5. Выбранный вид сохраняется в сессионном состоянии мастера

**Валидация:**
- Выбор вида обязателен

**Результат:** В сессионном состоянии сохранён `speciesId` и `subspeciesId` (если применимо).

---

#### 2.1.2. Шаг 2: Выбор происхождения (Background)

**Поток:**
1. Система загружает список всех доступных происхождений
2. Пользователь выбирает происхождение
3. Выбранное происхождение сохраняется в сессионном состоянии

**Результат:** Сохранён `backgroundId`.

---

#### 2.1.3. Шаг 3: Выбор класса (Class)

**Поток:**
1. Система загружает список всех доступных классов
2. Пользователь выбирает класс
3. Если класс выбирает подкласс на 1-м уровне — система показывает выбор подкласса
4. Если класс даёт выбор навыков:
   - Система показывает список навыков из `class.skills.from`
   - Пользователь выбирает ровно `class.skills.count` навыков
5. Выбранный класс и навыки сохраняются в сессионном состоянии

**Валидация:**
- Выбор класса обязателен
- Количество выбранных навыков должно равняться `class.skills.count`

**Результат:** Сохранены `classId`, `subclassId` (если выбран), `selectedSkills[]`.

---

#### 2.1.4. Шаг 4: Распределение характеристик (Ability Scores)

**Поток:**
1. Система показывает 6 характеристик с базовыми значениями в зависимости от выбранного метода:
   - **Standard Array:** `[15, 14, 13, 12, 10, 8]` — пользователь распределяет их по характеристикам перетаскиванием
   - **Point Buy:** все значения `8`, доступно 27 очков. Стоимость повышения: 8→9 (1), 9→10 (1), 10→11 (1), 11→12 (1), 12→13 (1), 13→14 (2), 14→15 (2). Максимум 15 (до применения бонусов).
   - **Manual:** свободный ввод 3–18 для каждой характеристики
2. Пользователь распределяет значения
3. Система автоматически применяет бонусы от вида и происхождения:
   - Для каждого `AbilityScoreIncrease` из `species.ability_score_increases` и `background.ability_score_increases`:
     - Если `optional = false`: прибавить `increase` к указанной характеристике
     - Если `optional = true`: пользователь выбирает, к какой характеристике применить (но не к той, что уже имеет +2 от вида)
4. Итоговые значения (после бонусов) не могут превышать 20

**Валидация:**
- Все 6 характеристик должны иметь значение
- Для Point Buy: сумма потраченных очков ≤ 27
- Для Manual: каждое значение в диапазоне 3–18
- Итоговое значение (после бонусов) ≤ 20

**Вычисляемые значения (пересчитываются автоматически):**
- Модификатор характеристики = `floor((score - 10) / 2)`
- Бонус атаки заклинаний = `proficiency_bonus + spellcasting_ability_modifier`
- Сложность спасброска заклинаний (Spell Save DC) = `8 + proficiency_bonus + spellcasting_ability_modifier`

**Результат:** Сохранены `ability_scores: {str, dex, con, int, wis, cha}` и `selected_optional_increases`.

---

#### 2.1.5. Шаг 5: Выбор снаряжения (Equipment)

**Поток:**
1. Система собирает всё начальное снаряжение:
   - Из `class.starting_equipment` — массив `EquipmentChoice[]`
   - Из `background.equipment` — массив `EquipmentChoice[]`
2. Для каждого `EquipmentChoice`:
   - Если `options` несколько — показать выбор (radio-button)
   - Если `options` одна — автоматически выбрать
   - Если `count > 1` — выбрать несколько
3. Пользователь делает выбор для каждого пункта
4. Система также добавляет золото из `background` (если указано в происхождении)
5. Пользователь может добавить дополнительные предметы через кнопку «Добавить предмет» (открывает поиск по всем предметам)

**Валидация:**
- Для каждого `EquipmentChoice` с `count` должно быть выбрано ровно `count` опций

**Результат:** Сохранён `equipment[]` — массив `CharacterEquipment`.

---

#### 2.1.6. Шаг 6: Выбор заклинаний (только для кастеров)

**Предусловие:** `class.spellcasting != null`

**Поток:**
1. Система определяет количество заклинаний:
   - **Заговоры:** из `class.spellcasting.cantrips_known` для уровня 1
   - **Заклинания 1-го уровня:** из `class.spellcasting.spells_known` для уровня 1 (для known-кастеров) или `class.spellcasting.ability_modifier + 1` (для prepared-кастеров)
2. Система загружает список заклинаний, доступных классу
3. Пользователь выбирает заклинания (не более доступного количества)
4. Для prepared-кастеров выбор происходит из списка известных (весь классовый список)

**Валидация:**
- Количество заговоров = `cantrips_known` для уровня 1
- Количество заклинаний 1-го уровня = согласно формуле класса

**Результат:** Сохранены `spells: { cantrips[], prepared[] / known[] }`.

---

#### 2.1.7. Шаг 7: Детали персонажа

**Поток:**
1. Пользователь вводит:
   - Имя (обязательно)
   - Мировоззрение (опционально)
   - Портрет (опционально, из галереи/камеры)
   - Внешность (опционально)
   - Предыстория (опционально)
   - Заметки (опционально)

**Валидация:**
- Имя: не пустое, 1–100 символов, обрезается по пробелам в начале и конце

**Результат:** Сохранены `name`, `alignment`, `portrait`, `appearance`, `backstory`, `notes`.

---

#### 2.1.8. Шаг 8: Проверка и создание

**Поток:**
1. Система вычисляет все производные значения:
   - **HP (max):** `class.hit_die + CON_modifier`
   - **HP (current):** равно max
   - **Hit Dice:** `1d{hit_die}` (total = 1, remaining = 1)
   - **AC:** рассчитывается по формуле из экипированной брони или `10 + DEX_modifier`
   - **Инициатива:** `DEX_modifier`
   - **Скорость:** `species.speed`
   - **Proficiency Bonus:** +2 (для уровня 1)
   - **Навыки:** для каждого навыка вычислить бонус = `proficiency_bonus` (если proficient) + `ability_modifier`
   - **Спасброски:** `proficiency_bonus + ability_modifier` для proficient
   - **Пассивная внимательность:** `10 + perception_skill_bonus`
   - **Ячейки заклинаний:** из `class.spellcasting.spell_slots` для уровня 1
2. Система генерирует UUID для персонажа
3. Система формирует JSON-блоб `character.json` (см. Data Specification §6.1)
4. Система сохраняет запись в таблицу `characters` Room:
   - `id = UUID`
   - `name = name`
   - `json_data = <JSON-блоб>`
   - `created_at = now()`
   - `updated_at = now()`
5. Система очищает сессионное состояние мастера

**Валидация:**
- Имя не пустое
- Все обязательные поля заполнены

**Результат:**
- Персонаж сохранён в Room
- Пользователь перенаправлен на `CharacterSheet(new_id)`
- Snackbar: «Персонаж "Имя" создан»

**Ошибки:**
- **Ошибка записи в Room:** AlertDialog «Не удалось сохранить персонажа. Попробуйте снова.» Кнопка «Повторить» повторяет сохранение.

### 2.2. Редактирование персонажа

**Назначение:** Изменение данных существующего персонажа.

**Триггер:** Меню (⋮) → «Редактировать» на чар-листе, или долгое нажатие на карточку в списке.

**Предусловия:** Персонаж существует в Room.

**Входные данные:** `characterId` (UUID).

**Поток:**
1. Система загружает персонажа из Room по `characterId`
2. Парсит JSON-блоб в структуру `Character`
3. Открывает экран редактирования со списком секций (аналогично шагам мастера создания)
4. Пользователь выбирает секцию для редактирования
5. Система открывает соответствующий экран редактирования с предзаполненными данными
6. Пользователь вносит изменения
7. При возврате из секции (кнопка «Назад») — изменения немедленно сохраняются в Room:
   - `json_data = <обновлённый JSON>`
   - `updated_at = now()`

**Особые случаи:**
- Изменение вида → пересчёт ability scores, traits, languages, speed
- Изменение класса → пересчёт hit die, saving throws, skills, features, spellcasting, spell slots
- Изменение характеристик → пересчёт всех модификаторов, навыков, спасбросков, spell attack/DC
- Изменение уровня → пересчёт proficiency bonus, HP, spell slots, features

**Пересчёт при изменении:**
При любом изменении, затрагивающем вычисляемые значения, система выполняет полный пересчёт:
1. Модификаторы характеристик
2. Бонус мастерства (зависит от уровня)
3. Навыки (proficiency + ability_mod + expertise)
4. Спасброски (proficiency + ability_mod)
5. Spell Attack Bonus и Spell Save DC
6. Max HP (пересчитывается только если изменился CON mod или уровень)
7. AC (пересчитывается если изменился DEX mod или броня)
8. Инициатива (DEX mod)
9. Пассивная внимательность

**Результат:**
- Персонаж обновлён в Room
- Чар-лист обновлён (если открыт)

**Ошибки:**
- **Ошибка записи в Room:** изменения не сохраняются, пользователь остаётся на экране редактирования, Snackbar с ошибкой.

### 2.3. Удаление персонажа

**Назначение:** Безвозвратное удаление персонажа.

**Триггер:** Меню (⋮) → «Удалить» на чар-листе, или свайп влево на карточке в списке, или долгое нажатие → «Удалить».

**Предусловия:** Персонаж существует в Room.

**Входные данные:** `characterId`.

**Поток:**
1. Система показывает диалог подтверждения:
   - Заголовок: «Удалить персонажа?»
   - Текст: «Персонаж "Имя" будет безвозвратно удалён. Это действие нельзя отменить.»
   - Кнопка «Удалить» (красная, `filled`)
   - Кнопка «Отмена» (`outlined`)
2. Пользователь нажимает «Удалить»
3. Система удаляет запись из таблицы `characters` по `characterId`
4. Система удаляет все связанные данные (избранное персонажа не хранится отдельно, оно в JSON-блобе)
5. Система возвращает пользователя на экран списка персонажей
6. Snackbar: «Персонаж "Имя" удалён» с кнопкой «Отменить» (на 5 секунд)

**Отмена удаления (undo):**
- При нажатии «Отменить» в Snackbar — система восстанавливает запись в Room

**Результат:**
- Запись удалена из Room
- Пользователь на экране списка персонажей

**Ошибки:**
- **Ошибка удаления из Room:** AlertDialog, персонаж не удалён.

### 2.4. Копирование персонажа

**Назначение:** Создание копии существующего персонажа.

**Триггер:** Меню (⋮) → «Дублировать» на чар-листе или в списке.

**Предусловия:** Персонаж существует в Room.

**Входные данные:** `characterId`.

**Поток:**
1. Система загружает персонажа из Room
2. Создаёт глубокую копию JSON-блока
3. Генерирует новый UUID
4. Изменяет имя: `"{original_name} (копия)"`
5. Устанавливает `created_at = now()`, `updated_at = now()`
6. Сохраняет новую запись в Room
7. Snackbar: «Создана копия персонажа»
8. Пользователь остаётся на текущем экране

**Результат:**
- Новая запись в Room
- Пользователь не перенаправляется (может открыть копию из списка)

### 2.5. Импорт персонажа

**Назначение:** Импорт персонажа из внешнего JSON-файла.

**Триггер:** Кнопка «Импортировать» на пустом состоянии списка персонажей, или экран «Импорт данных» в настройках.

**Входные данные:** JSON-файл (выбранный через системный файловый менеджер).

**Поток:**
1. Система открывает системный файловый менеджер с фильтром `application/json`
2. Пользователь выбирает файл
3. Система читает содержимое файла
4. **Валидация структуры:**
   - Проверка, что файл — валидный JSON
   - Проверка наличия обязательных полей: `id`, `name`, `version`, `class_id`, `level`, `species_id`, `ability_scores`
   - Проверка типов полей
   - Проверка диапазонов: `level` ∈ [1, 20], `ability_scores.*` ∈ [3, 30]
5. **Проверка ссылок:**
   - Для каждого `class_id`, `species_id`, `background_id`, `subclass_id` — проверить существование объекта в загруженных пакетах
   - Для каждого `item_id` в `equipment` — проверить существование
   - Для каждого `spell_id` в `spells` — проверить существование
   - Отсутствующие ссылки → warning (не блокирует импорт)
6. **Разрешение конфликтов:**
   - Если `id` уже существует в Room → диалог: «Персонаж с таким ID уже существует. Создать копию с новым ID?»
     - «Да» → генерируется новый UUID
     - «Нет» → импорт отменяется
7. Система сохраняет персонажа в Room
8. Snackbar: «Персонаж "Имя" импортирован»

**Ошибки:**
- **Невалидный JSON:** AlertDialog «Файл повреждён или имеет неверный формат.»
- **Отсутствуют обязательные поля:** AlertDialog с перечнем отсутствующих полей
- **Некорректные значения:** AlertDialog с перечнем некорректных значений
- **Ошибка чтения файла:** AlertDialog «Не удалось прочитать файл. Проверьте права доступа.»

**Результат:**
- Персонаж сохранён в Room
- Пользователь остаётся на экране импорта или списка персонажей

### 2.6. Экспорт персонажа

**Назначение:** Экспорт персонажа в JSON-файл для обмена или резервного копирования.

**Триггер:** Меню (⋮) → «Экспортировать» на чар-листе или в списке.

**Входные данные:** `characterId`.

**Поток:**
1. Система загружает персонажа из Room
2. Формирует JSON-файл в соответствии со схемой `character.json` (Data Specification §6.1)
3. Обновляет `updated_at` до текущего времени
4. Формирует имя файла: `HeroCraft24_{character_name}_{YYYY-MM-DD}.json`
   - Имя персонажа нормализуется: заменяются пробелы на `_`, удаляются спецсимволы
5. Открывает системный ShareSheet / Save File диалог
6. Пользователь выбирает путь сохранения
7. Система записывает файл

**Ошибки:**
- **Ошибка записи файла:** Snackbar «Не удалось сохранить файл. Проверьте свободное место и права доступа.»
- **Пользователь отменил сохранение:** операция прерывается без ошибки

**Результат:**
- JSON-файл сохранён в выбранную пользователем директорию

### 2.7. Повышение уровня

**Назначение:** Увеличение уровня персонажа с пересчётом всех зависимых параметров.

**Триггер:** Нажатие на уровень персонажа в чар-листе → кнопка «+», или кнопка «Повысить уровень» в секции класса.

**Предусловия:**
- `character.level < 20`
- Персонаж существует в Room

**Входные данные:** `characterId`.

**Поток:**
1. Система увеличивает `level` на 1
2. Система определяет новый `proficiency_bonus` по таблице:

   | Уровень | Бонус мастерства |
   |---|---|
   | 1–4 | +2 |
   | 5–8 | +3 |
   | 9–12 | +4 |
   | 13–16 | +5 |
   | 17–20 | +6 |

3. **Увеличение HP:**
   - Система показывает диалог: «Увеличение очков здоровья»
   - Текст: «Бросок: 1d{hit_die} + {CON_mod}. Среднее: {average}»
   - Кнопки: «Бросить» (случайное значение), «Среднее» (average, округлённое вверх), «Вручную» (пользователь вводит значение)
   - Выбранное значение прибавляется к `hp.max`
   - `hp.current` также увеличивается на то же значение

4. **Hit Dice:**
   - `hit_dice.total` = `"{level}d{hit_die}"`
   - `hit_dice.remaining` увеличивается на 1

5. **Новые умения (Features):**
   - Система проверяет `class.features` для нового уровня
   - Если есть умения на этом уровне — добавляет их ID в `features[]`
   - Если умение требует выбора (например, Fighting Style) — показывает диалог выбора

6. **Ability Score Increase (уровни 4, 8, 12, 16, 19):**
   - Система показывает диалог: «Увеличение характеристик»
   - Пользователь может:
     - Увеличить одну характеристику на 2
     - Увеличить две характеристики на 1
     - Взять черту (Feat) вместо увеличения
   - Если выбрана черта — она добавляется в `feats[]`

7. **Новые заклинания (для кастеров):**
   - Система проверяет `class.spellcasting` для нового уровня
   - Если добавляются новые известные заклинания/подготовки — показывает диалог выбора
   - Если добавляются новые ячейки — обновляет `spell_slots`

8. **Пересчёт всех вычисляемых значений (см. §2.2)**

9. Система сохраняет персонажа в Room
10. Snackbar: «Уровень повышен до {level}!»

**Особые случаи:**
- **Уровень 20:** кнопка «Повысить уровень» скрывается
- **Мультиклассирование:** (не поддерживается в v1.0, зарезервировано для будущих версий)

**Ошибки:**
- **Ошибка сохранения:** AlertDialog, уровень не повышен.

**Результат:**
- `level` увеличен на 1
- Все вычисляемые значения пересчитаны
- Персонаж сохранён в Room

### 2.8. Управление характеристиками

**Назначение:** Изменение значений характеристик персонажа.

**Триггер:** Нажатие на секцию Ability Scores в чар-листе → кнопка «Редактировать», или экран редактирования персонажа → Характеристики.

**Предусловия:** Персонаж существует в Room.

**Входные данные:** `characterId`, новые значения характеристик.

**Поток:**
1. Система показывает текущие значения 6 характеристик
2. Пользователь изменяет значения
3. При изменении:
   - Пересчитываются модификаторы: `floor((score - 10) / 2)`
   - Пересчитываются все навыки: `proficiency_bonus + ability_mod` (если proficient)
   - Пересчитываются спасброски: `proficiency_bonus + ability_mod` (если proficient)
   - Пересчитывается Spell Attack Bonus и Spell Save DC (если кастер)
   - Пересчитывается AC (если зависит от DEX)
   - Пересчитывается инициатива
   - Пересчитывается пассивная внимательность
4. Система сохраняет персонажа в Room

**Валидация:**
- Каждое значение ∈ [1, 30] (теоретический максимум с магическими предметами)
- Без магических предметов: ∈ [3, 20]

**Результат:** Характеристики и все зависимые значения обновлены.

### 2.9. Управление навыками

**Назначение:** Изменение proficient/expertise статуса навыков.

**Триггер:** Нажатие на секцию Skills в чар-листе → кнопка «Редактировать».

**Предусловия:** Персонаж существует в Room.

**Поток:**
1. Система показывает список всех 18 навыков
2. Для каждого навыка отображается:
   - Название
   - Связанная характеристика
   - Текущий бонус
   - Статус: не proficient / proficient / expertise
3. Пользователь переключает статус (циклически: none → proficient → expertise → none)
4. При изменении пересчитывается бонус навыка

**Ограничения:**
- Expertise доступен только для навыков, уже имеющих proficiency (ограничение класса/черт)
- Некоторые классы дают expertise только для определённых навыков

**Результат:** Навыки обновлены, бонусы пересчитаны.

### 2.10. Управление спасбросками

**Поток:**

2. Proficient-спасброски отмечены иконкой (зависят от класса)
3. Пользователь не может изменить proficient-спасброски вручную (они определяются классом) — **только просмотр**
4. Бонус спасброска вычисляется: `proficiency_bonus + ability_mod` (если proficient), иначе `ability_mod`

**Результат:** Нет изменений (режим просмотра).

### 2.11. Управление классом и подклассом

**Назначение:** Изменение класса или подкласса персонажа.

**Триггер:** Экран редактирования → секция «Класс».

**Предусловия:** Персонаж существует в Room.

**⚠️ Важное ограничение v1.0:** Изменение класса существующего персонажа — **деструктивная операция**, которая сбрасывает:
- Все features класса
- Все заклинания
- Навыки (если выбранный класс даёт другой набор)
- Спасброски
- Hit Die и HP (пересчитываются заново)

**Поток:**
1. Система показывает диалог предупреждения:
   - «Изменение класса приведёт к сбросу умений, заклинаний и пересчёту HP. Продолжить?»
2. При подтверждении — система показывает список классов
3. Пользователь выбирает новый класс
4. Система пересчитывает:
   - Hit Die
   - HP (пересчитывается для всех уровней: 1-й уровень = max, остальные = average)
   - Saving Throws
   - Skills (сброс, затем выбор новых)
   - Features (все features нового класса в соответствии с уровнем)
   - Spellcasting (если есть)
   - Spell slots
5. Если выбран подкласс — добавляются его features
6. Система сохраняет персонажа

**Результат:** Класс изменён, все зависимые параметры пересчитаны.

### 2.14. Управление чертами

**Назначение:** Добавление и удаление черт (feats) персонажа.

   - Уже имеющиеся черты исключаются (если `repeatable = false`)

6. Система пересчитывает зависимые значения
7. Система сохраняет персонажа

**Удаление черты:**
1. Пользователь нажимает на черту в списке → диалог подтверждения
2. Система убирает эффекты черты
3. Черта удаляется из `feats[]`
4. Система пересчитывает зависимые значения
5. Система сохраняет персонажа

**Результат:** Черта добавлена/удалена.

### 2.15. Управление инвентарём

**Добавление предмета:**

### 2.17. Управление заклинаниями персонажа

**Назначение:** Подготовка/изучение заклинаний, использование ячеек.

**Триггер:** Нажатие на секцию Spells → «Управлять заклинаниями».

#### 2.17.1. Подготовка заклинаний (Prepared Casters)

**Применимо к:** Wizard, Cleric, Druid, Paladin, Artificer

**Поток:**
1. Система загружает все заклинания из классового списка
2. Отображает два списка:
   - **Доступные:** все заклинания класса, которые ещё не подготовлены
   - **Подготовленные:** текущие подготовленные заклинания
3. Количество подготовленных заклинаний = `spellcasting_ability_modifier + character.level` (минимум 1)
4. Пользователь перетаскивает заклинания между списками
5. Система не позволяет превысить лимит подготовленных
6. При сохранении — обновляется `spells.prepared[]`

#### 2.17.2. Изучение заклинаний (Known Casters)

**Применимо к:** Bard, Sorcerer, Warlock, Ranger, Arcane Trickster, Eldritch Knight

**Поток:**
1. Система загружает известные заклинания и доступные для изучения
2. При повышении уровня — показывает количество новых заклинаний для изучения
3. Пользователь выбирает заклинания из классового списка
4. При замене (для некоторых классов) — можно заменить одно известное заклинание на новое
5. При сохранении — обновляется `spells.known[]`

#### 2.17.3. Использование ячеек заклинаний

**Поток:**
1. Пользователь нажимает на ряд ячеек в секции Spells
2. Система показывает диалог с ячейками по уровням
3. Каждая ячейка — переключатель (использована / не использована)
4. Пользователь отмечает использованные ячейки
5. Система сохраняет состояние

**Восстановление ячеек:**
- **Long Rest:** все ячейки восстанавливаются
- **Short Rest (Warlock):** все Pact Magic ячейки восстанавливаются
- **Arcane Recovery (Wizard):** один раз в день, до половины уровня (округление вверх) суммарных уровней ячеек
- Кнопка «Reset All» в диалоге — сбрасывает все ячейки (для ручного восстановления)

### 2.18. Управление HP и временными HP

**Назначение:** Изменение текущих, максимальных и временных очков здоровья.

**Триггер:** Нажатие на HP-бар в Quick Stats.

#### 2.18.1. Изменение текущих HP

**Поток:**
1. Система показывает диалог с полями:
   - Текущие HP: `[число]`
   - Кнопки быстрого изменения: `[-10] [-5] [-1] [+1] [+5] [+10]`
2. Пользователь изменяет значение
3. **Ограничение:** `0 ≤ current_hp ≤ max_hp`
4. При попытке установить < 0 — значение фиксируется на 0
5. При попытке установить > max_hp — значение фиксируется на max_hp
6. Система сохраняет персонажа

**При падении до 0 HP:**
- Автоматически применяется состояние `unconscious`
- Автоматически применяется состояние `prone`
- Начинаются Death Saves (см. §2.19)
- Temp HP сбрасываются до 0

#### 2.18.2. Получение урона

**Поток:**
1. Пользователь вводит количество урона (или нажимает кнопки `[-X]`)
2. Система сначала вычитает урон из временных HP:
   - Если `temp_hp > 0`:
     - Если `damage <= temp_hp`: `temp_hp -= damage`, `damage = 0`
     - Если `damage > temp_hp`: `damage -= temp_hp`, `temp_hp = 0`, затем вычитается из `current_hp`
3. Затем вычитается оставшийся урон из `current_hp`
4. Если `current_hp` падает до 0 или ниже — см. «При падении до 0 HP»

#### 2.18.3. Лечение

**Поток:**
1. Пользователь вводит количество лечения (или нажимает `[+X]`)
2. Система прибавляет к `current_hp` (не превышая `max_hp`)
3. Если персонаж был при 0 HP:
   - `current_hp = healing_amount`
   - Состояния `unconscious` и `prone` снимаются
   - Death Saves сбрасываются (успехи = 0, провалы = 0)
4. Система сохраняет персонажа

#### 2.18.4. Изменение максимальных HP

**Поток:**
1. Пользователь изменяет `max_hp`
2. Если новое `max_hp < current_hp`: `current_hp = max_hp`
3. Если новое `max_hp > old_max_hp`: `current_hp += (new_max_hp - old_max_hp)`
4. Система сохраняет персонажа

#### 2.18.5. Временные HP

**Правила:**
- Временные HP **не складываются**. Если персонаж получает новые временные HP, а старые ещё есть — игрок выбирает, какие оставить (обычно большие)
- Приложение автоматически заменяет временные HP на большие

**Поток:**
1. Пользователь вводит значение временных HP
2. Если новое значение > текущих временных HP:
   - `temp_hp = new_value`
3. Если новое значение ≤ текущих:
   - Система показывает диалог: «У вас уже есть {current} временных HP. Заменить на {new}?»
4. Система сохраняет персонажа

**Результат:** HP и/или временные HP обновлены.

---

### 2.19. Death Saves

**Назначение:** Управление спасбросками от смерти при 0 HP.

**Автоматическое поведение:**
- Death Saves отображаются только когда `current_hp == 0`
- Счётчики появляются автоматически при падении до 0 HP

**Ручное управление:**
1. Пользователь нажимает на кружок успеха/провала
2. Кружок переключается (пустой → заполненный)
3. Система проверяет условия:
   - **3 успеха:** персонаж стабилизирован. `current_hp = 0`, но стабилен. Состояние `unconscious` остаётся. Счётчики смерти сбрасываются.
   - **3 провала:** персонаж мёртв. Показывается диалог: «Персонаж погиб.»
   - **Natural 1 (при броске):** считается за 2 провала
   - **Natural 20 (при броске):** персонаж восстанавливает 1 HP, состояния `unconscious` и `prone` снимаются, счётчики сбрасываются

**Получение урона при 0 HP:**
- Любой урон = 1 провал
- Критический удар = 2 провала
- Если урон ≥ `max_hp`: мгновенная смерть

**Результат:** Death Saves обновлены.

### 2.20. Управление состояниями

**Назначение:** Добавление и удаление состояний (Conditions) персонажа.

**Триггер:** Нажатие на секцию Conditions → «Добавить состояние».

**Добавление состояния:**
1. Система показывает список всех 15 состояний
2. Пользователь отмечает нужные состояния (мультивыбор)
3. Система добавляет ID состояний в `conditions[]`
4. Система сохраняет персонажа

**Удаление состояния:**
1. Нажатие на крестик (×) рядом с активным состоянием
2. Состояние удаляется из `conditions[]`
3. Система сохраняет персонажа

**Просмотр состояния:**
1. Нажатие на название состояния → Bottom Sheet с полным описанием эффекта

**Автоматические состояния:**
Система **не применяет** состояния автоматически (кроме `unconscious` и `prone` при 0 HP — см. §2.18). Игрок сам управляет состояниями в соответствии с правилами.

**Результат:** Состояния обновлены.

### 2.21. Управление истощением

**Назначение:** Изменение уровня истощения (Exhaustion).

**Триггер:** Нажатие на счётчик истощения в секции Conditions.

**Поток:**
1. Система показывает счётчик 0–6 с кнопками `[–]` и `[+]`
2. Пользователь изменяет уровень
3. **Эффекты истощения (D&D 2024):**

   | Уровень | Эффект |
   |---|---|
   | 1 | −1 ко всем d20 Tests (проверкам) |
   | 2 | −2 ко всем d20 Tests, −5 ft скорости |
   | 3 | −3, −10 ft скорости, Disadvantage на спасброски |
   | 4 | −4, −15 ft скорости, Disadvantage на атаки, HP halved |
   | 5 | −5, −20 ft скорости, скорость 0 |
   | 6 | Смерть |

4. Система сохраняет персонажа

**Примечание:** Эффекты истощения отображаются информационно, но не применяются автоматически к броскам (v1.0). Игрок учитывает их вручную.

**Результат:** Уровень истощения обновлён.

### 2.22. Использование Hit Dice

**Назначение:** Расходование Hit Dice для восстановления HP во время Short Rest.

**Триггер:** Нажатие «Short Rest» → диалог использования Hit Dice, или прямое нажатие на секцию Hit Dice.

**Поток:**
1. Система показывает диалог:
   - Доступно Hit Dice: `{remaining} / {total}`
   - Тип Hit Dice: `d{hit_die}`
   - Поле: «Использовать: [число]»
   - Кнопки: `[+1] [+5] [All]`
2. Пользователь выбирает количество
3. Ограничение: `0 ≤ use_count ≤ remaining`
4. При нажатии «Применить»:
   - Для каждого использованного Hit Dice:
     - Бросок: `random(1, hit_die) + CON_modifier`
     - Сумма добавляется к `current_hp`
   - `remaining` уменьшается на `use_count`
5. Система сохраняет персонажа

**Результат:**
- Восстановлено HP = сумма бросков
- Hit Dice уменьшены

### 2.23. Short Rest

**Назначение:** Короткий отдых (1 час), восстанавливающий ограниченные ресурсы.

**Триггер:** Кнопка «Short Rest» внизу чар-листа.

**Предусловия:** Персонаж существует в Room.

**Поток:**
1. Система показывает диалог подтверждения:
   - «Вы уверены, что хотите совершить Short Rest?»
   - «Персонаж может использовать Hit Dice для восстановления HP.»
2. Пользователь подтверждает
3. **Использование Hit Dice:** открывается диалог (§2.22)
4. Система восстанавливает способности, отмеченные как «восстанавливаются после короткого отдыха»:
   - Для каждого feature в `features[]`:
     - Проверить поле `short_rest_recovery` в данных класса
     - Если true — отметить как использованное = false
   - **Warlock:** все Pact Magic ячейки восстанавливаются
   - **Wizard (Arcane Recovery):** открывается диалог восстановления ячеек (один раз в день)
   - **Channel Divinity (Cleric/Paladin):** восстанавливается (если класс даёт)
   - **Wild Shape (Druid):** восстанавливается
5. Система сохраняет персонажа
6. Snackbar: «Короткий отдых завершён»

**Ограничения:**
- Нет ограничений на количество Short Rest в день (правила не ограничивают)

**Результат:**
- Использованы Hit Dice (по выбору игрока)
- Восстановлены short-rest способности
- Персонаж сохранён

### 2.24. Long Rest

**Назначение:** Длинный отдых (8 часов), полностью восстанавливающий персонажа.

**Триггер:** Кнопка «Long Rest» внизу чар-листа.

**Предусловия:** Персонаж существует в Room.

**Поток:**
1. Система показывает диалог подтверждения:
   - «Вы уверены, что хотите совершить Long Rest?»
   - «Восстанавливает: все HP, половину Hit Dice, все ячейки заклинаний и способности.»
2. Пользователь подтверждает
3. Система выполняет восстановление:
   - **HP:** `current_hp = max_hp`
   - **Временные HP:** `temp_hp = 0`
   - **Hit Dice:** `remaining = min(total_count, remaining + floor(total_count / 2))`
     - Возвращается половина от общего количества (минимум 1)
   - **Ячейки заклинаний:** все использованные → не использованные (для всех уровней)
   - **Способности:** все long-rest и short-rest способности восстановлены
   - **Истощение:** `exhaustion = max(0, exhaustion - 1)`
   - **Death Saves:** сброшены (0 успехов, 0 провалов)
   - **Состояния:** снимаются все состояния, кроме тех, что не снимаются отдыхом (определяется в данных состояния)
4. Система сохраняет персонажа
5. Snackbar: «Длинный отдых завершён»

**Ограничения:**
- Персонаж может получить пользу только от одного Long Rest в 24 игровых часа (приложение не отслеживает игровое время, это остаётся на усмотрение игрока)

**Результат:**
- Персонаж полностью восстановлен
- Сохранён в Room

## 3. Просмотр контента

### 3.1. Загрузка списков

**Назначение:** Загрузка и отображение списков игровых объектов (заклинания, предметы, монстры и т.д.).

**Триггер:** Открытие экрана списка (переход на таб, открытие подраздела справочника).

**Поток:**
1. Система проверяет состояние кэша:
   - Если кэш валиден (пакеты не менялись) → показать кэшированный список
   - Если кэш невалиден → перестроить
2. **Построение списка:**
   - Система читает `manifest.json` всех активных пакетов
   - Извлекает `objects.{type}[]` для запрошенного типа
   - Объединяет списки из всех пакетов
   - Применяет активные фильтры и сортировку
3. Система отображает список

**Иерархия загрузки:**
1. Manifest (быстро — индекс) → для списков
2. Полный JSON (лениво) → при открытии карточки

**Обновление списка:**
- Список обновляется при:
  - Изменении состава активных пакетов
  - Импорте нового пакета
  - Удалении пакета
  - Изменении фильтров/сортировки

**Кэширование:**
- Список кэшируется в памяти (InMemoryCache)
- Размер кэша: 500 объектов каждого типа
- LRU (Least Recently Used) — вытеснение наименее используемых
- Кэш инвалидируется при изменении пакетов

---

### 3.2. Открытие карточки объекта

**Назначение:** Загрузка и отображение полной информации об игровом объекте.

**Триггер:** Короткое нажатие на карточку в списке.

**Входные данные:** `fullId` (например, `"phb2024:fireball"`).

**Поток:**
1. Система парсит `fullId` на `packId` и `objectId`
2. Проверяет, активен ли пакет:
   - Если пакет отключён → ошибка «Пакет неактивен»
3. Проверяет кэш:
   - Если объект в кэше → вернуть из кэша
   - Если нет → загрузить
4. **Загрузка полного JSON:**
   - Система читает файл `packs/{packId}/{type_dir}/{objectId}.json`
   - Тип директории определяется по `type` объекта из манифеста
   - Парсит JSON в соответствующую модель
5. **Валидация при загрузке:**
   - Проверка обязательных полей
   - Проверка типов
   - Если ошибка — объект не загружается, показывается ошибка
6. **Разрешение ссылок:**
   - Для каждого поля-ссылки (например, `classes[]` в заклинании) система проверяет существование целевого объекта
   - Битые ссылки отображаются как `[Unknown]`, но не блокируют отображение
7. Система помещает объект в кэш
8. Система отображает карточку объекта

**Ошибки:**
- **Файл не найден:** AlertDialog «Объект не найден. Возможно, пакет был удалён.»
- **Ошибка парсинга JSON:** AlertDialog «Данные повреждены. Попробуйте переустановить пакет.»
- **Пакет отключён:** AlertDialog «Пакет отключён. Включите его в настройках.»

**Результат:** Объект загружен и отображён.

---

### 3.3. Переходы по связанным объектам

**Назначение:** Навигация к связанным объектам через перекрёстные ссылки.

**Триггер:** Нажатие на чип связанного объекта (например, класс `[Wizard]` в карточке заклинания).

**Входные данные:** `targetId` (полный ID целевого объекта).

**Поток:**
1. Система парсит `targetId` → `packId:objectId`
2. Определяет тип целевого объекта по манифесту
3. Определяет целевой экран для типа:
   - `spell` → таб «Заклинания» → SpellDetail
   - `class` → таб «Справочник» → ClassDetail
   - `item` → таб «Снаряжение» → EquipmentDetail
   - `species` → таб «Справочник» → SpeciesDetail
   - `background` → таб «Справочник» → BackgroundDetail
   - `feat` → таб «Справочник» → FeatDetail
   - `condition` → таб «Справочник» → ConditionDetail
   - `monster` → таб «Справочник» → MonsterDetail
   - `mechanic` → таб «Справочник» → MechanicDetail
   - `glossary` → таб «Справочник» → GlossaryDetail
4. Система выполняет межтабовую навигацию:
   - Переключает таб (если необходимо)
   - Добавляет целевой экран в back stack соответствующего таба
   - Передаёт `targetId` как аргумент навигации
5. Целевой экран загружает объект по `targetId` (см. §3.2)

**Обработка отсутствующих ссылок:**
- Если целевой объект не найден (битая ссылка) — чип отображается серым, не кликабелен
- Текст: `[Unknown]` вместо названия

**Обработка отключённых пакетов:**
- Если пакет целевого объекта отключён — диалог: «Пакет "{pack_name}" отключён. Включить?»
- «Да» → включение пакета → перезагрузка → переход
- «Нет» → отмена перехода

## 4. Поисковая система

### 4.1. Индексация

**Когда строится индекс:**
- При первом запуске приложения
- При импорте нового пакета
- При удалении пакета
- При включении/отключении пакета

**Индексируемые поля (для каждого типа объектов):**

| Тип | Индексируемые поля |
|---|---|
| `spell` | `name.*`, `short_description.*`, `description.*` (первые 500 символов), `tags[]`, `school`, `classes[]` (разрешаются в имена) |
| `item` | `name.*`, `short_description.*`, `description.*` (первые 500 символов), `tags[]`, `category`, `effects[]` |
| `class` | `name.*`, `short_description.*`, `description.*`, `tags[]`, `features[].name.*` |
| `species` | `name.*`, `description.*`, `tags[]`, `traits[].name.*` |
| `background` | `name.*`, `description.*`, `tags[]` |
| `feat` | `name.*`, `description.*`, `tags[]`, `benefits[].name.*` |
| `condition` | `name.*`, `description.*`, `tags[]`, `effects[]` |
| `monster` | `name.*`, `short_description.*`, `description.*`, `tags[]`, `creature_type`, `subtype`, `environment[]` |
| `mechanic` | `name.*`, `description.*`, `tags[]`, `category` |
| `glossary` | `name.*`, `description.*`, `tags[]` |

**Структура индекса:**
- Каждый объект представлен как документ с полями: `id`, `type`, `pack`, `name_en`, `name_ru`, `text` (объединённые description и другие поля), `tags`
- Индекс строится в памяти, оптимизирован для FTS

---

### 4.2. Выполнение поиска

**Входные данные:** `query` (строка), `type` (опционально — ограничение типом объекта).

**Поток:**
1. Система получает поисковый запрос от пользователя
2. **Debounce 300 мс** — поиск не выполняется во время ввода, ждёт паузу в 300 мс
3. **Токенизация запроса:**
   - Разбиение по пробелам и знакам препинания
   - Приведение к нижнему регистру
   - Удаление стоп-слов (a, the, and, or, of, in, to, for, with, on, at, by, is)
   - Минимальная длина токена: 2 символа
4. **Поиск:**
   - Каждый токен ищется независимо
   - **AND-логика:** все токены должны присутствовать в документе
   - **Префиксный поиск:** токен "fire" находит "fireball", "fire bolt", "fire shield"
   - **Case-insensitive:** "Fireball" = "fireball"
   - **Diacritic-insensitive:** "déjà" = "deja"
5. **Фильтрация по типу:**
   - Если указан `type` — поиск только по объектам этого типа
6. **Ранжирование результатов** (см. §4.3)
7. Система возвращает отсортированный список результатов

**Поиск по ID:**
- Если запрос точно соответствует формату `packId:objectId` или `objectId` — результат с точным совпадением ID поднимается вверх

**Поиск по тегам:**
- Теги ищутся как обычные токены (наравне с названием и описанием)

**Поиск по нескольким словам:**
- Все слова из запроса должны присутствовать (AND)
- Порядок слов не важен

**Поиск по частичному совпадению:**
- Токен "ball" находит "fireball" (префиксный поиск для каждого слова)
- "fire ball" находит "fireball" (токены "fire" и "ball" независимо)

---

### 4.3. Ранжирование результатов

**Формула релевантности (score):**

```
score = 0
for each token in query:
    if token matches name exactly:
        score += 100
    if token matches name as prefix:
        score += 50
    if token matches name anywhere:
        score += 30
    if token matches short_description:
        score += 10
    if token matches description:
        score += 5
    if token matches tags:
        score += 15
    if all tokens match in name:
        score *= 2.0  (boost for exact match)
```

**Порядок результатов:**
1. Сортировка по убыванию score
2. При равном score — по алфавиту (name)

**Максимальное количество результатов:** 100 (пагинация не используется в v1.0, но список виртуализирован LazyColumn)

---

### 4.4. Граничные случаи

| Случай | Поведение |
|---|---|
| **Пустой запрос** | Показать полный список (без поиска) |
| **Запрос из одного символа** | Показать все объекты, где этот символ встречается в названии (префикс) |
| **Запрос только из стоп-слов** | Показать «Ничего не найдено» |
| **Спецсимволы в запросе** | Игнорируются, поиск по оставшимся токенам |
| **Запрос длиннее 100 символов** | Обрезается до 100 символов |
| **Нет результатов** | Показать пустое состояние с предложением сбросить фильтры |

## 5. Система фильтрации

### 5.1. Логика фильтрации

**Принцип:**
- Фильтры внутри одной группы комбинируются через **OR**
- Разные группы фильтров комбинируются через **AND**

**Пример:**
```
Уровень: [0] OR [1]
AND
Школа: [evocation] OR [conjuration]
AND
Концентрация: [Да]
```

Означает: «Заговоры ИЛИ заклинания 1-го уровня, И школы эвокации ИЛИ вызова, И с концентрацией».

**Порядок применения фильтров:**
1. Сначала отбираются все объекты запрошенного типа из всех активных пакетов
2. Применяются фильтры (AND между группами, OR внутри группы)
3. Поверх отфильтрованного списка применяется поиск (если активен)
4. Результат сортируется

**Сохранение фильтров:**
- Фильтры сохраняются в памяти в течение сессии
- При уходе с экрана и возврате — фильтры восстанавливаются
- При переключении табов — фильтры сохраняются для каждого таба независимо
- При закрытии приложения — фильтры сбрасываются

**Сброс фильтров:**
- Кнопка «Сброс» в Bottom Sheet — сбрасывает все фильтры
- Чип «Все» для быстрых фильтров уровня — сбрасывает только фильтр уровня
- Сброс немедленно обновляет список

---

### 5.2. Комбинирование с поиском и сортировкой

**Порядок операций:**
```
[Все объекты] → [Фильтрация] → [Поиск] → [Сортировка] → [Результат]
```

1. **Фильтрация** — грубый отбор по категориальным признакам
2. **Поиск** — текстовый поиск поверх отфильтрованного списка
3. **Сортировка** — упорядочивание результата

**Пример:**
- Пользователь выбрал фильтр «Уровень 1–3», затем ввёл в поиске «fire»
- Результат: все заклинания 1–3 уровня, содержащие «fire», отсортированные согласно выбранной сортировке

**Взаимодействие:**
- Изменение фильтров **сбрасывает** поисковый запрос? Нет — поиск и фильтры применяются одновременно
- Очистка поиска **не сбрасывает** фильтры
- Изменение сортировки **не влияет** на фильтры и поиск

## 6. Система сортировки

**Назначение:** Упорядочивание списка объектов.

**Принцип:**
- Сортировка применяется к результату после фильтрации и поиска
- Пользователь выбирает поле и направление сортировки
- Сортировка сохраняется в памяти сессии

**Доступные способы сортировки:**

| Тип объектов | Поля сортировки |
|---|---|
| `spell` | `name` (А–Я / Я–А), `level` (возр. / убыв.), `school` (А–Я) |
| `item` | `name` (А–Я / Я–А), `rarity` (common → artifact / artifact → common), `cost` (возр. / убыв.), `category` (А–Я) |
| `monster` | `name` (А–Я / Я–А), `challenge_rating` (возр. / убыв.), `size` (tiny → gargantuan) |
| `class` | `name` (А–Я / Я–А) |
| `species` | `name` (А–Я / Я–А) |
| `feat` | `name` (А–Я / Я–А), `category` (origin → epic) |
| `background` | `name` (А–Я / Я–А) |

**Сортировка по умолчанию:**
- Заклинания: по уровню (возрастание), затем по названию
- Предметы: по названию (А–Я)
- Монстры: по CR (возрастание), затем по названию

**Сортировка null-значений:**
- `null` всегда в конце (независимо от направления)

**Сортировка строк:**
- Алфавитная, case-insensitive, locale-aware (используется `Collator` с текущей локалью)

## 7. Импорт данных

### 7.1. Импорт пакета

**Назначение:** Добавление нового пакета игровых данных из ZIP-архива.

**Триггер:** Кнопка «Импортировать пакет» в управлении пакетами (Настройки).

**Входные данные:** ZIP-файл, выбранный через системный файловый менеджер.

**Поток:**

#### 7.1.1. Чтение и проверка структуры

1. Пользователь выбирает ZIP-файл
2. Система распаковывает ZIP во временную директорию
3. **Проверка структуры ZIP:**
   - Наличие `pack.json` в корне архива → **обязательно**
   - Наличие `manifest.json` → **обязательно**
   - Если отсутствуют → ошибка «Неверная структура пакета»
4. **Чтение pack.json:**
   - Извлечение `pack_id`, `version`, `format_version`, `rules_version`
   - Проверка `format_version` на совместимость (должен быть ≤ текущей версии приложения)
   - Если `format_version` новее → ошибка «Пакет создан для более новой версии приложения»
5. **Чтение manifest.json:**
   - Парсинг всех `objects`
   - Подсчёт количества объектов

#### 7.1.2. Валидация объектов

Для каждого объекта в manifest:

1. Найти соответствующий JSON-файл в архиве
2. Проверить, что файл существует и читаем
3. Проверить, что JSON валиден
4. Проверить обязательные поля (по схеме для данного типа)
5. Проверить типы полей
6. Проверить enum-значения
7. Проверить числовые диапазоны
8. Проверить формат ID (`[a-z0-9_]+`)

**Накопление ошибок:**
- Все ошибки собираются в список
- Процесс не прерывается на первой ошибке
- Валидация продолжается для всех объектов

#### 7.1.3. Проверка перекрёстных ссылок

Для каждого объекта, содержащего ссылки:

1. Извлечь все поля-ссылки (например, `classes[]`, `references[]`, `item_id`, ...)
2. Для каждой ссылки:
   - Проверить, что целевой объект существует в импортируемом пакете ИЛИ в уже загруженных пакетах
   - Если нет → warning (не блокирует импорт)

#### 7.1.4. Проверка конфликтов

1. Проверить, существует ли уже пакет с таким `pack_id`
2. Если существует:
   - Показать диалог: «Пакет "{pack_id}" уже установлен.»
   - Опции: «Перезаписать», «Объединить», «Отменить»
   - **Перезаписать:** удалить старый пакет, установить новый
   - **Объединить:** объекты с одинаковыми ID заменяются новыми; объекты только в новом пакете добавляются; объекты только в старом остаются без изменений
   - **Отменить:** импорт прерывается

#### 7.1.5. Установка пакета

1. Создать директорию `packs/{pack_id}/` в хранилище приложения
2. Скопировать все файлы из временной директории
3. Зарегистрировать пакет в системе (добавить в список активных)
4. **Переиндексация:**
   - Добавить объекты нового пакета в поисковый индекс
   - Обновить кэш
   - Обновить индекс перекрёстных ссылок
5. Очистить временную директорию

#### 7.1.6. Итоговый результат

- **Диалог с результатами:**
  - «Пакет "{pack_name}" импортирован»
  - Количество объектов по типам
  - Количество warnings (если есть)
  - Кнопка «OK»

#### 7.1.7. Откат при ошибках

- Если ошибка возникла на этапе валидации (до установки) — временная директория очищается, никакие данные не изменены
- Если ошибка возникла на этапе копирования файлов — частично скопированные файлы удаляются
- Если ошибка возникла на этапе переиндексации — система возвращается к предыдущему индексу (сохранённому до импорта)

## 10. Менеджер пакетов

**Назначение:** Управление активными пакетами данных.

### 10.1. Подключение пакета

**Триггер:** Управление пакетами → переключатель «Активен».

**Поток:**
1. Пользователь переключает пакет в активный
2. Система загружает manifest пакета
3. Проверяет зависимости пакета:
   - Если есть неактивные зависимости → диалог: «Для пакета требуются: {dep_list}. Активировать их?»
   - «Да» → активировать все зависимости

4. Добавляет объекты пакета в поисковый индекс
5. Обновляет кэш
6. Обновляет индекс перекрёстных ссылок

### 10.2. Отключение пакета

**Поток:**
1. Пользователь переключает пакет в неактивный
2. Система проверяет, есть ли пакеты, зависящие от этого:
   - Если есть → диалог: «Пакеты {dep_list} зависят от этого пакета. Они будут отключены. Продолжить?»

   - Объекты из других пакетов, ссылающиеся на объекты отключённого пакета → ссылки становятся битыми (отображаются как `[Unknown]`)

**Триггер:** Управление пакетами → (⋮) → «Обновить» (для Homebrew-пакетов).

1. Система предлагает выбрать новый ZIP-файл
2. Выполняется импорт с флагом «обновление» (см. §7.1)
3. Старая версия заменяется новой
4. Переиндексация

### 10.4. Приоритет пакетов

**Правило:**
- Если два объекта из разных пакетов имеют одинаковый полный ID (`pack:object`) — это считается конфликтом
- Конфликт разрешается по приоритету:
  1. Пользовательские пакеты (Homebrew)
  2. Внешние пакеты
  3. Встроенные пакеты (assets)
- При одинаковом приоритете — пакет, загруженный позже, переопределяет более ранний

### 10.5. Порядок загрузки пакетов

1. Встроенные пакеты (assets)
2. Внешние пакеты (external storage)
3. Пользовательские пакеты (Homebrew)

Пакеты загружаются последовательно, с учётом зависимостей (топологическая сортировка).

## 11. Система избранного

**Назначение:** Сохранение объектов в избранное для быстрого доступа.

### 11.1. Добавление в избранное

**Триггер:** Нажатие на иконку ☆ (star) в карточке списка или в Top App Bar экрана деталей.

**Входные данные:** `objectId` (полный ID), `objectType` (тип объекта).

**Поток:**
1. Система проверяет, существует ли объект в загруженных пакетах
2. Если объект не существует (битая ссылка) → Snackbar «Объект не найден», операция отменяется
3. Проверка дубликата: если объект уже в избранном → операция интерпретируется как удаление (см. §11.2)
4. Система добавляет запись в таблицу `favorites`:
   - `object_id = fullId`
   - `object_type = type`
   - `added_at = now()`
5. Иконка меняется на `star_filled`
6. Snackbar: «Добавлено в избранное» (с кнопкой «Отменить»)

**Отмена (undo):**
- При нажатии «Отменить» в Snackbar — запись удаляется из Room, иконка возвращается

### 11.2. Удаление из избранного

**Триггер:** Нажатие на иконку ★ (star_filled).

**Поток:**
1. Система удаляет запись из таблицы `favorites` по `object_id`
2. Иконка меняется на `star`
3. Snackbar: «Удалено из избранного» (с кнопкой «Отменить»)

### 11.3. Хранение списка избранного

- Таблица `favorites` в Room
- Индексы: `object_id` (уникальный), `object_type`, `added_at`
- При удалении пакета — связанные записи в избранном **не удаляются** автоматически (объект может быть восстановлен)

### 11.4. Синхронизация после изменения данных

- При удалении объекта из пакета (Homebrew) — запись в избранном остаётся, но при попытке открыть объект показывается ошибка «Объект не найден»
- При повторном импорте объекта с тем же ID — запись в избранном автоматически восстанавливает связь

### 11.5. Очистка битых ссылок в избранном

**Триггер:** Фоновая операция при запуске приложения.

**Поток:**
1. Система проходит по всем записям в `favorites`
2. Для каждой проверяет существование объекта в загруженных пакетах
3. Если объект не существует — запись помечается как «битая» (но не удаляется)
4. Пользователь может увидеть битые записи в избранном (серая иконка) и удалить их вручную

## 12. Разрешение перекрёстных ссылок

**Назначение:** Получение полного игрового объекта по его строковому ID.

**API:** `ContentRepository.resolveReference(id: String): Result<GameEntity>`

### 12.1. Алгоритм разрешения

1. **Парсинг ID:**
   - Разделение на `packId` и `objectId` по символу `:`
   - Если формат неверный → ошибка «Неверный формат ID»
2. **Поиск пакета:**
   - Проверка, что пакет `packId` существует и активен
   - Если пакет не найден → ошибка «Пакет не найден»
   - Если пакет отключён → ошибка «Пакет отключён»
3. **Поиск объекта в манифесте:**
   - Поиск `objectId` в `manifest.objects.*` пакета
   - Если объект не найден → ошибка «Объект не найден»
4. **Загрузка полного JSON:**
   - Определение типа объекта по манифесту
   - Загрузка файла (с кэшированием)
5. **Возврат объекта**

### 12.2. Обработка отсутствующих ссылок

- Если ссылка не может быть разрешена → объект не загружается, но ссылка не блокирует отображение родительского объекта
- В UI битая ссылка отображается как `[Unknown]` (серый текст, не кликабельный)
- В лог записывается warning с деталями

### 12.3. Обработка отключённых пакетов

- Если пакет отключён → при попытке разрешить ссылку показывается диалог с предложением включить пакет
- Если пользователь соглашается → пакет активируется, ссылка разрешается
- Если отказывается → ссылка считается битой

### 12.4. Обработка устаревших ссылок

- Если объект был удалён, но ссылка на него осталась → битая ссылка
- При восстановлении объекта (повторный импорт) → ссылка автоматически восстанавливается

## 13. Резервное копирование

### 13.1. Создание резервной копии

**Триггер:** Настройки → «Создать резервную копию».

**Поток:**
1. Система показывает диалог с опциями:
   - ☐ Персонажи (все)
   - ☐ Избранное
   - ☐ Настройки
   - ☐ Пользовательские пакеты
2. Пользователь выбирает, что включить
3. Система собирает данные:
   - **Персонажи:** все записи из `characters` → JSON-массив
   - **Избранное:** все записи из `favorites` → JSON-массив
   - **Настройки:** все записи из `settings` → JSON-объект
   - **Пакеты:** копирование директорий пользовательских пакетов
4. Упаковка в ZIP:
   - `backup.json` — метаданные (дата, версия приложения, количество объектов)
   - `characters.json` — массив персонажей
   - `favorites.json` — массив избранного
   - `settings.json` — настройки
   - `packs/` — пользовательские пакеты
5. Имя файла: `HeroCraft24_backup_{YYYY-MM-DD_HHmm}.zip`
6. Сохранение в `Documents/HeroCraft24/backups/`
7. Snackbar: «Резервная копия создана»

### 13.2. Восстановление из копии

**Триггер:** Настройки → «Восстановить из копии».

**Поток:**
1. Выбор ZIP-файла
2. Чтение `backup.json` → предпросмотр содержимого
3. Диалог подтверждения: «Текущие данные будут заменены. Продолжить?»
4. **Восстановление (в транзакции):**
   - Очистка соответствующих таблиц Room
   - Вставка данных из бэкапа
   - Копирование пакетов (если выбраны)
   - Переиндексация
5. Если ошибка на любом шаге → откат (Room-транзакция), исходные данные сохраняются
6. Snackbar: «Данные восстановлены»

## 15. Справочник формул

### 15.1. Базовые формулы D&D 2024

| Параметр | Формула |
|---|---|
| **Модификатор характеристики** | `floor((score - 10) / 2)` |
| **Бонус мастерства** | `+2` (ур. 1–4), `+3` (5–8), `+4` (9–12), `+5` (13–16), `+6` (17–20) |
| **Бонус навыка** | `proficiency_bonus` (если proficient) + `ability_modifier` + `proficiency_bonus` (если expertise) |
| **Бонус спасброска** | `proficiency_bonus` (если proficient) + `ability_modifier` |
| **Пассивная внимательность** | `10 + perception_skill_bonus` |
| **Инициатива** | `DEX_modifier` |
| **КБ (без брони)** | `10 + DEX_modifier` |
| **КБ (с бронёй)** | `armor_base + DEX_modifier` (с учётом max_dex и stealth_disadvantage) |
| **HP на 1-м уровне** | `hit_die_max + CON_modifier` |
| **HP на новых уровнях** | `average(hit_die) + CON_modifier` (среднее = `(hit_die / 2) + 1`, округлённое вниз) или бросок |
| **Spell Attack Bonus** | `proficiency_bonus + spellcasting_ability_modifier` |
| **Spell Save DC** | `8 + proficiency_bonus + spellcasting_ability_modifier` |
| **Количество подготовленных заклинаний** | `spellcasting_ability_modifier + level` (минимум 1) |
| **Количество известных заговоров** | По таблице класса |
| **Ячейки заклинаний** | По таблице класса |

| Константа | Значение |
|---|---|
